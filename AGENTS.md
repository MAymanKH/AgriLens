# AgriLens | Instructions for teammates and AI agents

**Read order:** `START_HERE.md` first for approved decisions, canonical API contracts, the fallback policy and team-wide definition of done; then your exact file in `roles/` for owned tasks, examples, tests and references. If two documents disagree, follow `START_HERE.md` and report the conflict to the Technical Lead. Do not silently reconcile two incompatible field definitions.

1. **Build only your assigned area.** The Technical Lead owns rotation generation, comparison/ranking, public API and integration. Climate and Crop services only serve checked inputs. The app calls the Comparison API only. Research approves scientific evidence; Presentation owns narrative/media.
2. **Technology is not prescribed.** Use the team's existing choices; do not force a language, framework, database, hosting provider or tool on other owners. Each backend service must be independently runnable and testable using fixtures.
3. **Approved decisions are binding.** Check the decision register in `START_HERE.md`. For Pending scientific values, use clearly marked fixtures and request Research/Lead approval before presenting real outcomes. Never silently fill missing region coordinates, crop data, heat thresholds, or NASA periods.
4. **One authoritative API contract.** `START_HERE.md` owns shared field names, enums, units, errors, and meaning. Role-file example JSON is illustrative. Propose a change with exact before/after shape, reason, affected owners and tests; get consumer approval, plus Research sign-off if scientific. Update root contract, role mirrors and fixtures together.
5. **Use real evidence honestly.** Fake or synthetic fixture values are for development only. Never show them as NASA measurements. Unknown numeric values are `null` / **Not evaluated**, not zero. No made-up irrigation savings, forecasts, profits, yields or numeric soil-health claims.
6. **Implement the shared fallback behavior.** A valid baseline can have fewer than two alternatives; do not duplicate plans. Invalid inputs get useful errors; incomplete scenarios are unavailable; outages use only provenance-checked cache or retry state. The UI must not silently swap in old/mismatched results.
7. **Protect the demo.** Provide early fixtures, implement graceful failures, keep the last verified working build. After T+30 only fix issues that affect correctness, accessibility, deployment or the presentation. Milestones are elapsed hours after kickoff.
8. **Report at every handoff:** files changed; how to run/review; example request/response or screenshots; automated/manual tests and results; source/assumptions; open blockers; the next owner/action. Do not report a task done without evidence that passes its acceptance checks.
9. **Resolve conflicts quickly:** the service owner decides internal implementation; Research decides whether a scientific claim is supported; affected owners approve interface changes; the Technical Lead makes the final integration/scope call and records it in `START_HERE.md`.

**Project-wide acceptance:** the checklist in `START_HERE.md` is the shared definition of done. Passing a role's tasks alone does not mean the product is finished.
