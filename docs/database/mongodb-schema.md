# MongoDB schema reference

Status: Technical Lead implementation defaults. Native server startup is supplied in `tools/dev.py`; owners implement indexes, validators, importers, and adapters through their chosen drivers. [The design rationale](README.md) defines ownership. [The handoff](implementation-handoff.md) defines publication and acceptance. Root API contracts remain authoritative.

## Shared conventions

Document IDs are opaque, nonempty strings chosen by the owning importer. Daily document `_id` values may be generated by the driver. External region and crop IDs are stable strings, never MongoDB ObjectIds exposed to consumers.

| Field | Storage type | Meaning |
|---|---|---|
| `schema_version` | BSON integer | Storage shape, initially `1` |
| `decision_revision` | String | Exact Git commit containing the applicable approved decisions and method notes |
| `region` | Object | `{id, name, coordinates: {lat, lon}}`; copied from the approved decision |
| `kind` | String enum | `fixture` or `observed`; observed means source-backed data, including agricultural references |
| `status` | String enum | `staging`, `sealed`, `approved`, or `rejected` |
| `created_at` | BSON date | Import creation timestamp in UTC |
| `approval` | Object or null | `{research_record, technical_record, approved_at}`; research_record references scientific sign-off; technical_record references the importer validation report, without an extra approval meeting |
| `limitations` | Array of strings | Missing facts and restrictions on interpretation |

Both catalog and dataset manifests contain these fields. Timestamps in the JSON examples use Extended JSON `$date`. Ordinary `YYYY-MM-DD` strings identify climate days in the dataset's stated time standard, not UTC instants.

Numeric measurements use finite BSON numeric values, excluding NaN and infinity. Whole counts, months, years, and schema versions are integers. Missing quantitative facts are explicit `null`. Zero is a real measurement, never a missing-value sentinel.

Fixture documents cannot enter `approved` status or be selected by live services. Observed documents may still contain missing metrics when the root fallback policy permits them. Approval confirms the supported use and limitations, not completeness of every optional metric.

## `agrilens_crops.crop_catalogs`

One document contains one region's catalog revision. The current product publishes 4–6 eligible crops. Draft catalogs can contain fewer records but cannot become the live demo catalog until acceptance passes.

| Field | Type | Constraint |
|---|---|---|
| `_id` | String | Immutable catalog revision ID |
| Shared fields | See above | Required |
| `slot_order` | Array of strings | Exactly the four root slot IDs, in root order |
| `crops` | Array of objects | Unique crop IDs within the document |
| `sources` | Array of objects | Unique source IDs within the document |

Each crop contains exactly the domain fields required by the internal contract: `id`, `name`, `valid_seasons`, `grow_window`, `water_need_mm`, `family`, `is_legume`, and `source_ids`. `valid_seasons` is a nonempty subset of `summer` and `winter`. Each growing-window month is an integer from 1 to 12 or `null`. Start after end denotes a crossing of December, but the actual mapping to rotation years still requires the approved calendar rule. Equal months mean a same-month window unless an approved method says otherwise.

Water range endpoints are nonnegative numbers or `null`. When both are known, `min <= max`. An incomplete range is not a complete quantitative total. `family` is a string or `null`; `is_legume` is a boolean or `null`. A published crop's season and window must be verified. Unsupported entries stay in staging catalogs rather than the published eligible set.

Stored sources contain `{id, title, url, supports}`. `supports` is a nonempty description of the supported claims. The internal Crop adapter emits `{id, url, supports}` as contracted. Comparison obtains human-readable source titles from a version-controlled, Research-approved source ledger keyed by the same IDs. Missing ledger titles block release until resolved. Passing new source title fields through the API would require a separate consumer-approved contract change.

Synthetic staging example, intentionally incomplete and ineligible for live use:

```json
{
	"_id": "fixture-catalog-v1",
	"schema_version": 1,
	"decision_revision": "pending",
	"region": {"id": "sample_region", "name": "Fixture region", "coordinates": {"lat": null, "lon": null}},
	"kind": "fixture",
	"status": "staging",
	"created_at": {"$date": "2026-11-13T00:00:00Z"},
	"approval": null,
	"limitations": ["Synthetic structure only; no approved agricultural facts."],
	"slot_order": ["y1_summer", "y1_winter", "y2_summer", "y2_winter"],
	"crops": [{
		"id": "summer_a", "name": "Fixture summer crop", "valid_seasons": ["summer"],
		"grow_window": {"start_month": null, "end_month": null},
		"water_need_mm": {"min": null, "max": null},
		"family": null, "is_legume": null, "source_ids": []
	}],
	"sources": []
}
```

Read pattern: `findOne({_id: configured_catalog_id, status: "approved", kind: "observed"})`. The built-in unique `_id` index is sufficient for the current pinned read. No text, geospatial, or per-crop multikey index is needed. The importer checks uniqueness of embedded crop IDs and source IDs; a unique index is not a substitute for that array check.

## `agrilens_climate.climate_datasets`

One manifest describes a reproducible dataset revision. Its daily records reference the manifest's `_id` through `dataset_id`.

| Field | Type | Meaning |
|---|---|---|
| `_id` | String | Immutable dataset revision ID |
| Shared fields | See above | Required |
| `period` | Object | `{first_year, last_year}`, inclusive integers |
| `units` | Object | `{tmax: "C", rain: "mm/day"}` |
| `parameters` | Object | `{tmax, rain}` containing approved NASA parameter IDs |
| `provenance` | Object | Root `source_url`, `retrieved_at`, `missing_days`, `spatial_resolution`, `time_standard` |
| `raw_artifact` | Object | `{uri, sha256}` identifying retained original response bytes |
| `validation` | Object | `{method_ref, expected_days, record_count, complete_years, report_uri, normalized_sha256}` |
| `scenarios` | Object | Root `hottest_year` and `driest_year` objects with `{year, rule}` |

`provenance.retrieved_at` is a BSON date stored as an ISO timestamp on the wire. `missing_days` is the number of absent expected dates. It does not count a present date with a missing parameter. The validation report separately lists absent dates and missing or invalid temperature and rain fields, plus eligibility for each scenario. A complete date count alone cannot establish complete observations.

`validation.method_ref` resolves to the versioned, approved parameter, completeness, scenario-selection, and calendar methods. A rule string alone is not an executable definition. `complete_years` contains only years eligible under that method. A scenario's `year: null` means unavailable and cannot be advertised as supported. No year-selection formula is approved by this document.

The normalized checksum covers sorted daily records and all interpretation metadata, including coordinates, period, units, parameters, time standard, and method reference. The implementation specifies canonical serialization before calculating checksums. The raw checksum covers the original bytes. Neither checksum is an approval record.

Synthetic staging example; the year illustrates structure, not an approved NASA period:

```json
{
	"_id": "fixture-climate-v1",
	"schema_version": 1,
	"decision_revision": "pending",
	"region": {"id": "sample_region", "name": "Fixture region", "coordinates": {"lat": null, "lon": null}},
	"kind": "fixture",
	"status": "staging",
	"created_at": {"$date": "2026-11-13T00:00:00Z"},
	"approval": null,
	"limitations": ["Not NASA observations; period and methods are unapproved."],
	"period": {"first_year": 2020, "last_year": 2020},
	"units": {"tmax": "C", "rain": "mm/day"},
	"parameters": {"tmax": null, "rain": null},
	"provenance": {"source_url": null, "retrieved_at": null, "missing_days": null, "spatial_resolution": null, "time_standard": null},
	"raw_artifact": {"uri": null, "sha256": null},
	"validation": {"method_ref": null, "expected_days": null, "record_count": 1, "complete_years": [], "report_uri": null, "normalized_sha256": null},
	"scenarios": {"hottest_year": {"year": null, "rule": "Pending approval"}, "driest_year": {"year": null, "rule": "Pending approval"}}
}
```

Read pattern: `findOne({_id: configured_dataset_id, status: "approved", kind: "observed"})`. The built-in `_id` index is sufficient. Approved manifests require real coordinates, ordered years, parameter IDs, provenance, checksums, a validation report, method reference, and approval records. Fields that are nullable in staging are not thereby optional at publication.

## `agrilens_climate.climate_daily`

| Field | Type | Constraint |
|---|---|---|
| `_id` | Driver-generated ID | Private to storage |
| `schema_version` | Integer | Initially `1` |
| `dataset_id` | String | References one dataset manifest |
| `date` | String | Valid calendar date in `YYYY-MM-DD` format |
| `tmax_c` | Number or null | Missing temperature remains `null` |
| `rain_mm` | Number or null | Nonnegative when known; NASA missing sentinels become `null` |

Synthetic record belonging only to the fixture manifest above:

```json
{
	"schema_version": 1,
	"dataset_id": "fixture-climate-v1",
	"date": "2020-01-01",
	"tmax_c": null,
	"rain_mm": null
}
```

Required unique compound index: `{dataset_id: 1, date: 1}`. It prevents duplicate dates within a dataset, supports equality on dataset plus date ranges, and supports ascending date reads. Dates can repeat across distinct dataset revisions. No region/date unique index is used because it would prevent retaining corrected history.

Read pattern: `find({dataset_id: configured_dataset_id}).sort({date: 1})`. Date validity, membership in the declared period, finite values, sentinel conversion, and completeness are importer checks. MongoDB does not enforce the logical parent reference; the importer and publication checks do. Daily records cannot change after sealing. Orphaned staging imports are not eligible for service reads.

## Validation and API adaptation

MongoDB validators use `$jsonSchema`, `validationLevel: "strict"`, and `validationAction: "error"` for supported types, required fields, enums, and basic bounds. Services and importers validate cross-field, cross-document, scientific, and reference constraints at their boundaries. Database validators alone cannot prove Research approval or source validity.

The implementing owner writes the actual validator for the pinned server version. This document specifies requirements, not an installed validator. Unknown schema versions fail closed. Extra stored fields do not automatically become API fields; adapters explicitly project the root fields. Extensions that acquire meaning receive a schema-version change.

| Endpoint | Mapping from storage |
|---|---|
| `/internal/crops` | Manifest `region.id` -> `region_id`; `slot_order`, approved `crops`, contracted `sources` |
| `/internal/climate` | Manifest `region.id` -> `region_id`; `region.coordinates` -> `coordinates`; `period`, `units`, `scenarios`, `provenance`; daily rows projected to `{date,tmax_c,rain_mm}` |
| `/api/config` | Lead's versioned region/sample configuration plus eligible crops and supported scenarios from internal APIs |
| `/api/compare` | Calculated response only; no MongoDB document is returned directly |

Source IDs must resolve. Crop citations use the approved title ledger described above. NASA provenance URLs map to stable, approved source IDs and titles in that same ledger. An ID collision with conflicting evidence blocks release. Climate and Crop storage metadata stays private; Comparison uses the pinned release record for reproducibility without requiring new wire fields.

Unknown regions map to `UNKNOWN_REGION`. Missing evidence for a known region maps to `INSUFFICIENT_DATA`. Unavailable advertised scenarios use the root scenario errors. Storage outages map to retryable `SERVICE_UNAVAILABLE`. No approved revision means no fixture substitution and no automatic selection of an older revision.
